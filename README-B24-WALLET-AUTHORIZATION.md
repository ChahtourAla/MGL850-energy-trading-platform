# B24-A1 offline authorization reservation

B24-A1 and B24-A2 were independently accepted within the offline prototype scope; the full B24 changes remain under verification. B23 has not been deployed to Hedera. The evaluator only accepts the authenticated `b24_evaluator` role on the marked, loopback-only `b22_disposable_review` database. The approved deployment and `SIMULATED_TEST` spending policy in the test are synthetic fixtures, not real consent or a verified live deployment.

`apps/backend/scripts/b24a1-authorization.mjs` reads the finalized archived B22 market and its one authoritative plan, reuses the Python-free B22 reconciliation, independently checks all persisted allocations with the B21 helpers, and rebuilds the B23 commitment. Preview is read-only. Explicit `execute:true` locks the buyer/deployment nonce domain and policy/deployment rows, checks the approved fixture and exact limits, reserves a nonce and bounded deadline, creates unsigned B23 terms and inserts a durable reservation. Identical retries return the stored terms only while the policy, deadline and deployment remain eligible. Revoked or expired policies, expired deadlines and retired deployments return explicit blocked states; the historical RESERVED record, nonce, identity and reserved budget remain unchanged. `inspectReservation` is a read-only audit view and does not evaluate current eligibility. There is no signing, token approval, transfer, settlement intent or chain submission.

Use `powershell -NoProfile -ExecutionPolicy Bypass -File tools/b24a1-run-postgres-tests.ps1` from the repository root. It creates a new labeled local PostgreSQL 17 container, applies migrations only there, executes the real B22-A/B22-B and B24-A1 services, then removes only that owned container. It requires local Prisma, Python, Docker and a freshly compiled B23 Hardhat artifact. See `docs/B24-A-SPENDING-POLICY-DESIGN.md`, `B24A_SECURITY_INVARIANTS.md`, and `B24A_TEST_EVIDENCE.md`.

The offline signing, funding and allowance services described below extend this foundation. Real user consent, a verified live deployment and B25 execution/reconciliation are not provided. A future signer must independently revalidate stored terms, policy and chain state; reservation is not confirmation of payment.

Before any future B24-B signature, the signer must independently verify the current policy status and scope, policy and authorization expiration, deployment activation, the complete authoritative allocation plan and B23 plan commitment, the EIP-712 domain and digest, and reservation identity, nonce and deadline. A raw reservation alone never authorizes signing. Preview is a point-in-time check and cannot protect a later signing operation from revocation.

## B24-A2 read-only signing preflight

`verifySigningPreflight(client, {reservationId})` independently reads archived evidence and the complete authoritative plan as `b24_preflight` on the marked disposable database. It reconstructs the B23 commitment and typed-data digest, checks the fixture deployment, policy, budget, nonce and deadline, and returns only simulation eligibility. It never signs. See `docs/B24-A2-SIGNING-PREFLIGHT-DESIGN.md` and `B24A2_TEST_EVIDENCE.md`.

## Offline B24 services

The staged B24 implementation is an offline prototype for a marked disposable PostgreSQL database and local Hardhat chain. `b24-signing.mjs` independently checks the B24-A2 preflight, policy and deployment, and signs with a registry-generated ephemeral buyer. Keys remain in memory. The signed authorization and events are committed before release; a later revocation does not invalidate a signature already released on-chain.

`b24-funding.mjs` uses an independently approved fixture funding grant and shared buyer/token/minter budget. It reads the local balance, reserves the operation and sender nonce, and mints only the bounded shortfall. `b24-allowance.mjs` uses the registered buyer to approve only the reservation amount or reduce it to zero. Both use restricted database identities and append-only operation events. A `VERIFIED` event is asserted by a separate trusted receipt verifier after checking the local transaction, canonical block, token event and historical balance or allowance effect. PostgreSQL itself cannot prove the chain receipt.

A local session stores an approved reservation, deployment, buyer, runtime code hashes and anchor block. A restored session rechecks the actual local chain. If a transaction outcome is uncertain, the operation stays unresolved; recovery searches bounded local blocks for the reserved sender and nonce and validates the original transaction without broadcasting again. A missing or conflicting transaction remains unresolved.

`inspectLocalReadiness` revalidates the authorization, signature, local session, canonical receipts, balance and allowance. `READY_FOR_LOCAL_SETTLEMENT` is simulation-only and is not a payment confirmation or live Hedera authority. No V2 settlement intent or confirmation is created. The local B23 `settle` call belongs to the test; a production worker and chain reconciliation belong to B25.

Run `powershell -NoProfile -ExecutionPolicy Bypass -File tools/b24-wallet-bound-postgres.ps1` from the repository root with Docker Desktop, the existing dependencies and local Hardhat artifacts. It creates and removes only its own labeled disposable container. See `docs/B24-COMPLETE-WALLET-SECURITY-DESIGN.md`, `B24_SECURITY_INVARIANTS.md`, `B24_TEST_EVIDENCE.md` and `B24_END_TO_END_REPORT.md` for evidence and limitations.

The approver, signer process, local provider, receipt verifier and database owner are trusted prototype principals. Live consent, key custody, production deployment, token funding and Hedera receipt verification are not enabled. A raw reservation or a simulated signature is not independent human consent.
