# B22-A database and concurrency evidence

The B22-A service is restricted to a marked disposable database and separately authenticated runtime roles. `B22HourlyRegistry` is immutable after insertion; its trigger derives the approver from `session_user` and serializes revisions with an advisory lock. `B22Ingestion` binds the authenticated ingestion principal, archived generated payload, content digest, generator/configuration hashes, roster and finalized V2 snapshot. The owner or superuser remains trusted; these controls do not protect against owner compromise. `tools/b22a-runtime-grants.sql` must be applied by an owner after separately provisioning non-owner runtime roles; the test harness does this only in its own disposable container.

The writer invokes the controlled local generator outside the write transaction. In a single transaction it locks the logical market and roster, rechecks profiles, inserts the pending V2 snapshot and its complete measurements, checks the canonical B21 hash, finalizes, and inserts the audit. Failure rolls back all these writes. B21 triggers prevent subsequent measurement changes. Corrections require an approved new roster revision and an authoritative B21 plan blocks correction. No settlement intent is created by the service.

`inspectHistoricalHour` checks archived payload digest, immutable source references, roster membership, measurement count and hash, and correction-chain structure without invoking the generator or consulting current profiles. Unknown market-only or pending drafts are reported `QUARANTINED` and are neither promoted nor removed.

The B22-A PostgreSQL harness exercises two real overlapping service calls with different approved revisions: the stale request pauses at its transaction boundary while the newer request commits; it then fails on the changed roster. Database readback verifies one snapshot, one audit and stable replay. In another service-level test the ingestion pauses immediately before finalization. An unapproved insert against its uncommitted snapshot fails with `P0001: snapshot does not exist`. A second insert waits on a disposable test-only advisory-lock trigger; after the service commits, the B21 guard rejects it with `P0001: measurements require pending snapshot`. The test checks the exact approved user set, canonical hash and one matching audit. The test lock coordinates the race; it is not claimed to be a lock acquired by the production service.

Other harness checks cover separately authenticated roles, no runtime schema/trigger privileges, transaction rollback on injected failure, immutable measurements, identical concurrent calls, roster revision racing ingestion, a committed correction, correction after a synthetic existing authoritative plan, profile changes, generator-unavailable replay and unknown draft quarantine. A test-scoped subprocess substitution reports an unsupported generator version and confirms it is rejected; an actual installed-release upgrade was not exercised. Tests do not prove every possible interleaving, physical meter accuracy, on-chain behavior or protection against privileged database operators.
