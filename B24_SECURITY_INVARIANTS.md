# B24 offline security invariants

- The accepted B24-A2 preflight is a point-in-time simulation check. The signer independently rechecks authorization and uses database locks around the signing decision and a further release check.
- Test wallets are generated within the in-memory registry. The registered buyer must match the archived B22 address. No private key is returned or stored. The runtime is not production custody.
- A signed authorization can remain valid on-chain after a later database revocation. PostgreSQL does not perform signature recovery; the signer and readiness verifier recover the buyer independently.
- Policy/deployment approval, signing, funding, allowance, receipt verification and read-only preflight use separate authenticated PostgreSQL identities. Their fixed-search-path functions and immutable records enforce database boundaries; the database owner and approved roles remain trusted.
- Local chain sessions bind the reservation, deployment, buyer, runtime bytecode hashes and an anchor block. Session restoration verifies the chain. Receipts are checked against the current canonical block because a later reorganization may preserve the session anchor.
- Local funding is bounded by an approver-created per-operation grant and shared buyer/token/minter budget. The funding service reads actual token balance under the budget lock. A funding reservation is retained even if its result is uncertain.
- Allowance is limited to the exact reservation amount or zero. The spender and token come from the approved deployment. Pending changes are serialized across reservations sharing the buyer/token/spender domain, and block readiness across that domain. Decreasing the allowance is permitted after policy revocation or deployment retirement.
- Funding and allowance reserve an immutable sender/nonce identity before broadcast. A conservative database-wide sender/nonce uniqueness rule prevents reuse even across fixture sessions. No uncertain operation is automatically resubmitted.
- Missing transaction hashes can be located by scanning at most 10,000 approved local blocks for the recorded sender and nonce and checking the exact calldata. If no matching mined transaction is found, the state remains unresolved. A lost ephemeral wallet cannot be reconstructed after process restart.
- Receipt evidence is an assertion by the trusted verifier, not a blockchain proof made by PostgreSQL. The application checks receipt success, token events, transaction terms, canonical block and historical balance/allowance effects. Successful readiness rechecks the receipts and actual current balance and allowance.
- Readiness is simulation-only and never means settlement confirmed. No V2 settlement intent or evidence is fabricated. B25 remains responsible for live execution and reconciliation.

Coverage limitations: the integrated scenario exercises one B22 buyer across two historical markets and tests shared-budget contention. All provider hangs, crash points and all combinations of role and chain failures need additional independent review. Local fixture policies are not real consent; a verified live deployment and production custody do not exist.
