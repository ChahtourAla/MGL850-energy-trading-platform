# B21 design and review evidence

B20 baseline: `f605e66dfb0d745d1fcf174004ddb594f9fa196a`. Existing V1 JSON schemas, matching engine, escrow, deployment artifacts and historical migrations remain separate. The original staged B21 migration is preserved unchanged; the additive `20261119010000_b21_snapshot_plan_integrity` migration aborts on existing finalized V2 snapshots or V2 allocations. This protects unknown prior data from silent conversion, but means an already populated V2 environment needs a separately reviewed migration. Only this session's disposable targets have been inspected; absence of external applications is not independently established.

## Facts and plans

`V2SnapshotMeasurement` has a snapshot/user primary key, same-market composite foreign key, valid user FK and nonnegative Wh checks. Its trigger locks the snapshot and only permits writes while pending. A finalization trigger disallows direct final inserts and requires complete counts and the canonical hash of persisted readings; its snapshot-row lock serializes concurrent measurement writes. `V2Position` remains an accounting projection and must not be treated as source truth. Measurement hash validity proves content integrity, not metering truth or data-source authorization.

`V2AllocationPlan` stores immutable manifest JSON and its hash, references one finalized same-market snapshot, and has `DRAFT`, `SUPERSEDED` and `AUTHORITATIVE` states. A partial unique index and trigger allow only one irrevocable authoritative plan per market. Plans begin as drafts; nonpayable alternatives may be superseded. Allocations are tied to a plan, snapshot and market, cannot be added after activation, and must reference matching buyer/seller roles and wallet addresses in the committed manifest. Settlement intent creation requires the authoritative plan and preserves the existing per-allocation uniqueness and evidence protections. Corrections can be prepared as drafts but switching a previously authorized plan or compensating payments requires a future policy.

The database checks each manifest's market, snapshot hash and interval, participant membership and Wh against immutable readings, and recomputes its versioned canonical SHA-256 hash. Matching parameters and participant fields are canonical ASCII strings with explicit nulls, UUID ordering and decimal encoding. Python/Node fixtures contain a base manifest and 29 economically significant changes; PostgreSQL checks all 30 hashes against the same vectors. This is a commitment, not a pricing-policy approval or guarantee that source readings are true.

## Verification

The disposable PostgreSQL 17.11 harness applies eleven migrations with Prisma 7.10.0 to a fresh database and checks Prisma drift. It separately executes original B21 regression tests on the original B21 schema. For a third database it applies the eight legacy SQL migrations, inserts synthetic legacy records, records those migrations in a disposable Prisma ledger with `migrate resolve`, then deploys all three B21 migrations. It compares nine legacy table dumps and checks representative indexes, foreign keys, joined reads and no legacy-to-V2 conversion. No application database or actual blockchain state is involved.

`tools/b21-postgres-safety.sql` checks each intended SQLSTATE and, for important trigger failures, exact error messages. `tools/b21-correction-postgres.sql` checks draft/finalized measurement boundaries, measured hash and manifest mismatches, authoritative plan exclusivity, draft payment refusal, sealing, supersession and a separately committed corrected snapshot with independent readings. `tools/b21-correction-concurrency.mjs` observes PostgreSQL lock waits when finalization races measurement INSERT/UPDATE/DELETE and when plans compete for activation. These tests do not prove all interleavings or blockchain exactly-once settlement.

The additive `20261119020000_b21_payment_readiness` migration preserves the two previously staged migrations. It refuses existing allocations or authoritative plans rather than silently reinterpreting them. New allocations start `PLANNED`, may become `VALIDATED` or `CANCELLED`, and a cancelled allocation cannot be reactivated. An authoritative plan cannot contain planned allocations; settlement intents require a validated allocation in the authoritative plan. The triggers serialize these operations using the market row. They compare each allocation's versions, individual buyer demand, seller supply, price bounds and energy preference against its immutable manifest. The V1 preference rule is `ANY` or the seller's exact energy type. Individual limits do not enforce aggregate quantities; B22 must enforce those in its matching transaction. Contextual Node/Python checks perform the same comparison only when the trusted manifest context is supplied; database triggers remain authoritative for persistence.

The first two B21 draft migrations have only been confirmed on disposable databases used in this session; their application in independent persistent environments is unknown. Do not apply the additive migration to a populated V2 environment without a separately reviewed upgrade.

Remaining work before live payments: trusted source validation, B22 matching/aggregate checks and pricing/dust policy, B23 deployed contract domain, B24 authorization/prefunding, and B25 authenticated chain verification, journal recovery and reconciliation. Live Hedera state, production API integration against a populated database and fresh Solidity compilation are not covered by these isolated checks.
