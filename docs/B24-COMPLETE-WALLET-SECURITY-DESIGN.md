# B24 offline wallet security design

B24 starts with the accepted B22 immutable historical allocation, B24-A1 reservation and independent B24-A2 preflight. All database execution paths are restricted to the marked `b22_disposable_review` database and separately authenticated non-owner fixture roles. No production signer or live Hedera path is enabled.

The in-memory registry generates ephemeral buyer wallets before B22 roster approval. The signing service independently reconstructs the EIP-712 terms, locks the policy and deployment, checks the local session, signs only with the archived buyer and records the authorization and ordered events before release. The signing commit orders authorization against revocation. A subsequent revocation cannot invalidate an already released on-chain signature. PostgreSQL checks signature structure, not ECDSA; consumers independently recover the buyer.

Local sessions are approved by the fixture approver and bind a reservation, deployment, buyer, transaction anchor and runtime hashes. Session restoration checks the canonical anchor and deployed code. The approver and internally supplied local provider are trusted. A reset invalidating the anchor fails closed; receipts are checked independently because a revert can leave the anchor intact while removing later transactions.

Funding uses an approved grant and a shared budget scoped to buyer, token and minter. Database locks serialize budget use and policy decisions. Funding and allowance operations reserve immutable sender nonces before submission, with a conservative database-wide sender/nonce uniqueness constraint. Allowance is limited to the exact reservation amount or zero. The local test minter is supplied by trusted harness code; no real key is accessed.

PostgreSQL and the local chain cannot commit atomically. A prepared operation is never automatically broadcast again after uncertainty. If a hash is known, receipt recovery checks it. If a broadcast happened before the hash was stored, bounded local block scanning locates the reserved sender/nonce and verifies the exact calldata before attaching the hash. If no matching canonical transaction can be established, the operation remains unresolved. The nonce reservation is not automatically released. A process restart loses ephemeral buyer private keys; it can recover existing transactions but cannot generate new signatures for those lost keys.

Receipt evidence is append-only and is written only via a separate authenticated local verifier. The verifier checks transaction calldata, recipient, sender, token events, canonical block, and historical balance/allowance effects. The verifier and database owner can lie; PostgreSQL cannot independently establish chain truth. Reconciliation of a previously submitted transaction remains possible after policy revocation or deployment retirement and does not authorize a new payment.

Readiness checks the current authorization, signed digest, current canonical local receipts, balance, allowance and unresolved journal state. It reports simulation-only readiness, not finality or payment. No B25 confirmation is created by B24. Future live use requires verified deployment identity, genuine consent, controlled keys, independently reviewed funding and allowance policy, chain-aware reconciliation and operational authorization.
